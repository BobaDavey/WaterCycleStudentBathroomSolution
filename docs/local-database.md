# Local database safety

Development uses a persistent PGlite database in `.local/data`. Vercel uses the managed PostgreSQL connection in `DATABASE_URL`; the local database and its demo data are never a production storage option.

PGlite supports one process per data directory. Stop the current server before starting another server or running the demo seed. For independent instances, set a distinct `LOCAL_DATABASE_PATH` for each instance. Browser tests already use a separate database.

WaterCycle places an exclusive `.watercycle.lock` file beside each local data directory. It records the owning process and, on Linux, its boot and process-start identity. A second live opener is refused. Locks from a dead process or a restored snapshot can be reclaimed automatically. Only the owner removes its lock when closing. SIGTERM and SIGINT initiate database close; let the server finish shutting down before restarting it.

If a local database cannot open, preserve the entire directory before attempting recovery. Never delete or reseed it automatically: it may contain student records. Restore a known-good backup, or choose a new `LOCAL_DATABASE_PATH` for a fresh demo. The demo seed requires `LOCAL_DATABASE=true` and refuses to run against `DATABASE_URL`.

Fresh Codespaces run `npm run dev:setup` automatically after dependency installation. This creates missing `teachertest` and Active `teststudent` accounts (development-only password `1234567890`), their two Monday–Friday Eastern classes (`DEMO1` — Demo Biology Morning, 7:00 AM–1:00 PM; `DEMO2` — Demo Chemistry Afternoon, 1:00 PM–6:00 PM), Approved enrollments in both, and question banks. Normal registrations receive a server-assigned username, join classes afterward, and need each teacher’s approval. Standalone setup, seeding, local diagnostics and local administrator provisioning load the same development environment files as Next.js. Neither managed database URLs nor hosted settings are allowed for demo setup; all managed connections are refused inside Codespaces.

Use `npm run dev:doctor` with the server stopped for a read-only check of local configuration, migrations, demo passwords, status and enrollment. Changed passwords and statuses are deliberately preserved. To get a completely new demo without destroying existing records, choose a new ignored `LOCAL_DATABASE_PATH`, then rerun setup.

Development setup automatically provisions the single required Developer username from private `DEV_ADMIN_INITIAL_PASSWORD`, or the existing `ADMIN_INITIAL_PASSWORD` name if the development-specific secret is absent. No privileged password is generated or written into source. Missing secrets do not block demo teacher/student creation. Use GitHub Codespaces secrets and restart the Codespace after configuring one. See the README for repository-level and per-user secret access limits.

Fresh local databases retain the original single-administrator identity constraint, unique index, and deletion/rename/demotion/disable protections. No managed schema migration is needed. Databases created by the previous optional local-administrator workflow keep their existing accounts; setup refuses to rename them or create a second administrator. Use a new `LOCAL_DATABASE_PATH` for a separate fresh demo if needed.

`npm run dev` prepares local demo data before launching Next.js, so skipped post-create setup produces an actionable failure rather than an empty login database. The post-start hook repeats setup when idle and preserves a database already held by a running server. Stop/restart the dev server after new secret injection. `npm run dev:check` verifies the configured private secret without logging its value; `dev:doctor` remains an alias. The optional hidden-prompt `dev:admin` recovery command remains local-only; production `admin:bootstrap` remains a separate managed-database operator command. Neither managed application startup nor builds seed accounts or consume development secrets.
